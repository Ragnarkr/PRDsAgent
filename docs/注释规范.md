# 注释规范（v1.0）

## 1. 文档目的
为 PRDsAgent 项目建立统一注释标准，确保代码在可读性、可维护性、可测试性和可运维性上达标，减少“注释缺失”和“注释失真”导致的返工。

## 2. 适用范围
- 适用于本仓库所有后续代码与脚本（含 Python、Go、Shell、配置生成脚本）。
- 适用于功能代码、测试代码、构建与运维脚本。
- 不要求对显而易见的简单赋值/遍历写解释性注释。

## 3. 六角色评审结论（会议纪要）
### 3.1 产品经理（PO）
- 注释必须帮助理解业务规则与边界条件，避免“代码能跑但业务含义不清”。
- 对需求术语应保持一致，必要时在注释中引用需求条目或规则编号。

### 3.2 技术负责人（Tech Lead）
- 注释重点应放在设计取舍（why）、约束条件和风险，而不是重复代码动作（what）。
- 涉及性能、安全、降级、幂等、重试策略的逻辑必须有注释说明。

### 3.3 开发工程师（Dev）
- 注释应可执行、可维护，避免大段“说明文档式注释”与代码脱节。
- 对复杂流程、状态机、非直观算法，要求模块级或函数级注释。

### 3.4 测试工程师（QA）
- 可测试行为必须可追溯：输入、输出、异常路径、边界值处理应在注释中可定位。
- FIXME/TODO 必须可追踪到 owner 与 issue，避免长期悬挂。

### 3.5 项目经理（PM）
- 注释规范作为交付质量门禁的一部分，纳入 PR 检查。
- 关键模块应定期做注释有效性抽检，降低维护风险。

### 3.6 运维工程师（DevOps）
- 涉及部署、配置、资源限制、超时、重试、告警阈值的代码必须注释清楚。
- 与生产稳定性相关的“危险默认值”必须显式说明。

## 4. 通用规则（MUST/SHOULD/MUST NOT）
### 4.1 MUST（必须）
- 注释解释“为什么这样做、约束是什么、风险在哪里”。
- 复杂函数必须包含简要说明：用途、关键输入、关键输出、错误处理。
- 涉及业务规则映射处，注明规则来源（需求文档章节/规则名/ADR）。
- 临时方案必须带失效条件与清理计划。

### 4.2 SHOULD（建议）
- 优先使用短小、贴近代码的注释，避免离代码过远的说明。
- 注释语言与项目主文档保持一致（中文优先，必要时可附英文术语）。
- 一处复杂逻辑最多保留一个“核心解释注释”，避免噪音。

### 4.3 MUST NOT（禁止）
- 禁止注释仅复述代码字面含义。
- 禁止保留与当前行为不一致的过期注释。
- 禁止无 owner、无时间、无追踪编号的 TODO/FIXME。

## 5. 何时必须写注释
- 跨边界集成：外部 API、模型网关、消息队列、存储协议映射。
- 业务关键规则：验收标准判定、冲突检测口径、评分/分级规则。
- 异常与降级逻辑：超时、重试、熔断、回退、幂等处理。
- 性能敏感路径：批处理、并发控制、缓存策略、限流策略。
- 安全合规路径：鉴权、脱敏、审计、权限边界。

## 6. TODO/FIXME 规范
统一格式：

```text
TODO(owner, due:YYYY-MM-DD, issue:#123): 后续动作
FIXME(owner, issue:#123): 当前缺陷与修复方向
```

要求：
- `owner` 必填（人名或角色）。
- `issue` 必填（任务号、工单号或缺陷号）。
- `due` 对 TODO 建议必填；到期未处理必须在迭代会上说明。

## 7. 语言级建议
### 7.1 Python
- 公共模块、公共函数使用 docstring。
- 复杂分支前使用 1-2 行行内注释解释分支目的。
- 避免在每一行都写注释，保持注释密度可读。

示例：

```python
def evaluate_acceptance(rule_set, doc):
    """按规则集评估需求验收标准，返回可测试性评分与问题列表。"""
    # 先执行确定性规则，保证基线稳定，再调用模型评估补充语义问题
    ...
```

### 7.2 Go
- 导出类型/函数必须有注释，且注释以标识符名开头。
- 并发、锁、channel 生命周期必须注释关键约束。
- 生产默认值（超时、重试次数）必须说明依据。

示例：

```go
// ReviewService evaluates requirement documents and returns structured issues.
type ReviewService struct { ... }

// Analyze runs rule checks first and then model evaluation to keep deterministic baseline.
func (s *ReviewService) Analyze(ctx context.Context, in Input) (Output, error) {
    ...
}
```

## 8. PR 审查清单（注释维度）
- 是否存在“只复述代码”的无效注释。
- 是否存在“代码已改但注释未改”的失真注释。
- 复杂逻辑是否说明了设计原因与边界。
- TODO/FIXME 是否满足可追踪格式。
- 关键异常、降级、安全、性能逻辑是否已注释。
